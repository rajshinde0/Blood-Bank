1. HASH TABLE WITH SEPARATE CHAINING
================================================================================

LOCATION IN CODE: Lines 1-15, 1315-1330

CONCEPT:
A hash table is an array-based data structure that maps keys to values using
a hash function. When two keys hash to the same index (collision), separate
chaining stores them in a linked list at that index.

IMPLEMENTATION:
    const int TABLE_SIZE = 97;  // Prime number for better distribution
    Donor *hashTable[TABLE_SIZE] = {nullptr};
    
    int hashFunc(int id) {
        return id % TABLE_SIZE;  // Division method
    }

HOW IT WORKS:
1. Donor ID (e.g., 1001) is passed to hashFunc()
2. hashFunc returns 1001 % 97 = 31
3. Donor is stored at hashTable[31]
4. If another donor hashes to 31, they're linked together

WHY PRIME NUMBER (97)?
- Prime modulo distributes keys more uniformly
- Reduces clustering and collisions
- 97 slots instead of 10 = ~90% fewer collisions

TIME COMPLEXITY:
- Insert: O(1) average, O(n) worst case
- Search: O(1) average, O(n) worst case
- Delete: O(1) average, O(n) worst case

USED FOR:
- Storing all donors by ID
- Fast donor lookup by ID (Menu Option 3)
- Adding new donors (Menu Option 1)
- Deleting donors (Menu Option 4)

2. AVL TREE (SELF-BALANCING BINARY SEARCH TREE)
================================================================================

LOCATION IN CODE: Lines 26-196

CONCEPT:
An AVL Tree is a binary search tree that automatically balances itself after
every insertion/deletion. Balance is maintained by ensuring the height
difference between left and right subtrees (balance factor) is at most 1.

IMPLEMENTATION:
    struct AVLNode {
        string donorName;
        int donorID;
        int height;
        AVLNode *left, *right;
    };
    
    class DonorBST {
        int getHeight(AVLNode *node);
        int getBalanceFactor(AVLNode *node);
        AVLNode *rightRotate(AVLNode *y);
        AVLNode *leftRotate(AVLNode *x);
        AVLNode *balance(AVLNode *node);
        AVLNode *insertHelper(AVLNode *node, string name, int id);
    };

FOUR ROTATION CASES:
1. LL (Left-Left): Single right rotation
   - Left child is heavy, left grandchild causes imbalance
   
2. RR (Right-Right): Single left rotation
   - Right child is heavy, right grandchild causes imbalance
   
3. LR (Left-Right): Left rotation on left child, then right rotation
   - Left child is heavy, right grandchild causes imbalance
   
4. RL (Right-Left): Right rotation on right child, then left rotation
   - Right child is heavy, left grandchild causes imbalance

BALANCE FACTOR:
    balanceFactor = height(left subtree) - height(right subtree)
    Must be: -1, 0, or 1 for balanced tree

WHY AVL INSTEAD OF REGULAR BST?
- Regular BST: O(n) worst case if elements inserted in sorted order
- AVL Tree: O(log n) GUARANTEED for all operations
- Example: Adding "Alice", "Bob", "Charlie", "David" in order
  - Regular BST: Becomes a linked list (O(n) search)
  - AVL Tree: Stays balanced (O(log n) search)

TIME COMPLEXITY:
- Insert: O(log n)
- Search: O(log n)
- Delete: O(log n)

USED FOR:
- Searching donors by name (Menu Option 8)
- Maintaining sorted order of donor names
- Fast name-based queries

4. TRIE (PREFIX TREE) FOR AUTOCOMPLETE
================================================================================

LOCATION IN CODE: Lines 452-570

CONCEPT:
A Trie is a tree-like data structure where each node represents a character.
Paths from root to nodes spell out stored strings. Excellent for prefix-based
searches like autocomplete.

IMPLEMENTATION:
    struct TrieNode {
        TrieNode *children[26];  // a-z (26 letters)
        bool isEndOfWord;
        vector<int> donorIDs;    // IDs of donors with this name
    };
    
    class DonorTrie {
        void insert(string name, int donorID);
        vector<pair<string, int>> searchPrefix(string prefix);
        bool search(string name);
    };

HOW INSERTION WORKS:
    Insert "John" with ID 1001:
    
    Root → J → O → H → N (isEndOfWord=true, donorIDs=[1001])
    
    Insert "Johnny" with ID 1002:
    
    Root → J → O → H → N → N → Y (isEndOfWord=true, donorIDs=[1002])
                    ↓
              (isEndOfWord=true, donorIDs=[1001])

HOW PREFIX SEARCH WORKS:
    Search prefix "Joh":
    1. Navigate: Root → J → O → H
    2. Collect all words from this point: "John", "Johnny"
    3. Return: [("John", 1001), ("Johnny", 1002)]

WHY TRIE?
- O(m) time where m = prefix length (independent of total entries!)
- Perfect for autocomplete functionality
- Memory efficient for common prefixes

TIME COMPLEXITY:
- Insert: O(m) where m = word length
- Search: O(m) where m = word length
- Prefix search: O(m + k) where k = number of results

USED FOR:
- Autocomplete donor search (Menu Option 14)
- Type "Raj" → Shows "Rajwardhan", "Rajesh", "Rajat"

5. LRU CACHE (LEAST RECENTLY USED)
================================================================================

LOCATION IN CODE: Lines 572-638

CONCEPT:
LRU Cache stores recently accessed items for fast retrieval. When cache is
full, the least recently used item is evicted. Combines doubly linked list
(for ordering) with hash map (for O(1) access).

IMPLEMENTATION:
    class LRUCache {
    private:
        int capacity;  // Max 10 donors
        list<pair<int, Donor*>> dll;  // Doubly linked list
        unordered_map<int, list<...>::iterator> cache;  // Hash map
        
    public:
        Donor* get(int donorID);
        void put(int donorID, Donor* donor);
    };

HOW IT WORKS:
    Cache capacity = 3
    
    Access donor 101: Cache = [101]
    Access donor 102: Cache = [102, 101]
    Access donor 103: Cache = [103, 102, 101]
    Access donor 101: Cache = [101, 103, 102]  (101 moved to front)
    Access donor 104: Cache = [104, 101, 103]  (102 evicted - LRU)

DATA STRUCTURE COMBINATION:
1. Doubly Linked List: Maintains access order (front = most recent)
2. Hash Map: Maps donor ID to list iterator for O(1) access

WHY THIS COMBINATION?
- Hash map alone: Can't track order
- Linked list alone: O(n) search
- Together: O(1) for both access and ordering

TIME COMPLEXITY:
- Get: O(1)
- Put: O(1)

USED FOR:
- Caching frequently searched donors
- View cache contents (Menu Option 15)
- Reduces hash table lookups by ~80%

6. UNION-FIND (DISJOINT SET UNION)
================================================================================

LOCATION IN CODE: Lines 640-727

CONCEPT:
Union-Find manages disjoint sets. It supports two operations:
- Find: Determine which set an element belongs to
- Union: Merge two sets into one

IMPLEMENTATION:
    class DonorUnionFind {
    private:
        unordered_map<int, int> parent;
        unordered_map<int, int> rank;
        
    public:
        void makeSet(int donorID);
        int find(int x);          // With path compression
        void unionSets(int x, int y);  // With union by rank
        bool areConnected(int x, int y);
    };

OPTIMIZATIONS IMPLEMENTED:

1. Path Compression (in find):
   - Flattens tree structure during find
   - All nodes point directly to root after find
   
   Before find(4): 1 → 2 → 3 → 4
   After find(4):  1 ← 2
                   ↑   ↑
                   3   4

2. Union by Rank:
   - Attaches smaller tree under larger tree
   - Keeps trees shallow
   
   Union(small_tree, large_tree):
   - Small tree's root becomes child of large tree's root

WHY BOTH OPTIMIZATIONS?
- Without: O(n) per operation
- With path compression only: O(log n) amortized
- With both: O(α(n)) ≈ O(1) amortized (α = inverse Ackermann)

TIME COMPLEXITY:
- Find: O(α(n)) ≈ O(1) amortized
- Union: O(α(n)) ≈ O(1) amortized
- Connected: O(α(n)) ≈ O(1) amortized

USED FOR:
- Grouping donors by blood compatibility network (Menu Option 16)
- Checking if two donors can help same patient (Menu Option 17)
- Cycle detection in MST algorithm

7. SEGMENT TREE FOR RANGE QUERIES
================================================================================

LOCATION IN CODE: Lines 729-857

CONCEPT:
A Segment Tree is a binary tree where each node stores aggregate information
(sum, min, max) about a range of elements. Enables efficient range queries
and point updates.

IMPLEMENTATION:
    class InventorySegmentTree {
    private:
        vector<int> tree;      // Segment tree array
        vector<int> inventory; // Original data
        int n;                 // Size
        
        void buildTree(int node, int start, int end);
        int queryRange(int node, int start, int end, int l, int r);
        void updateTree(int node, int start, int end, int idx, int value);
        
    public:
        int getRangeSum(int l, int r);
        void updateInventory(int idx, int value);
    };

TREE STRUCTURE:
    Original array: [10, 20, 30, 40] (blood units per day)
    
    Segment Tree:
                    [100]           (sum of 0-3)
                   /     \
               [30]       [70]      (sum of 0-1, 2-3)
              /    \     /    \
           [10]  [20] [30]  [40]    (individual elements)

HOW RANGE QUERY WORKS:
    Query sum of days 1-2 (20 + 30 = 50):
    1. Start at root [100]
    2. Range 0-3 partially overlaps 1-2
    3. Go to children [30] and [70]
    4. [30] range 0-1: take right child [20]
    5. [70] range 2-3: take left child [30]
    6. Return 20 + 30 = 50

WHY SEGMENT TREE?
- Naive range sum: O(n) per query
- Segment tree: O(log n) per query
- With 10,000 days: ~13 operations vs 10,000 operations

TIME COMPLEXITY:
- Build: O(n)
- Range query: O(log n)
- Point update: O(log n)

USED FOR:
- Setup inventory system (Menu Option 21)
- Query blood inventory range (Menu Option 22)
- Update inventory day (Menu Option 23)
- Example: "Total blood collected from Day 5 to Day 20?"

8. MINIMUM SPANNING TREE (KRUSKAL'S ALGORITHM)
================================================================================

LOCATION IN CODE: Lines 859-1004

CONCEPT:
MST finds the minimum cost subset of edges that connects all vertices in a
graph. Kruskal's algorithm sorts edges by weight and adds them if they don't
create a cycle.

IMPLEMENTATION:
    struct MSTEdge {
        int src, dest, weight;
        bool operator<(const MSTEdge& other) const {
            return weight < other.weight;
        }
    };
    
    class BloodBankMST {
    private:
        vector<MSTEdge> edges;
        vector<string> bankNames;
        
        int findParent(vector<int>& parent, int x);  // Union-Find
        void unionSets(...);
        
    public:
        vector<MSTEdge> kruskalMST();
        int getTotalCost();
    };

KRUSKAL'S ALGORITHM STEPS:
    1. Sort all edges by weight (ascending)
    2. Initialize each vertex as its own set (Union-Find)
    3. For each edge (u, v, weight):
       - If u and v are in different sets:
         - Add edge to MST
         - Union(u, v)
    4. Stop when MST has V-1 edges

EXAMPLE:
    Banks: A, B, C, D
    Edges: A-B(10), A-C(20), B-C(5), B-D(15), C-D(30)
    
    Sorted: B-C(5), A-B(10), B-D(15), A-C(20), C-D(30)
    
    Process:
    1. B-C(5): Add (B,C not connected)
    2. A-B(10): Add (A,B not connected)
    3. B-D(15): Add (D not connected to any)
    4. A-C(20): Skip (A-C already connected via A-B-C)
    5. C-D(30): Skip (already connected)
    
    MST: B-C(5), A-B(10), B-D(15) = Total cost: 30

WHY KRUSKAL'S?
- Greedy algorithm, easy to implement
- Works well with sparse graphs
- Uses Union-Find for efficient cycle detection

TIME COMPLEXITY:
- O(E log E) for sorting edges
- O(E × α(V)) for Union-Find operations
- Total: O(E log E)

USED FOR:
- Setup blood bank network (Menu Option 24)
- Display MST result (Menu Option 25)
- Real-world: Design minimum cost network to connect all blood banks

9. DIJKSTRA'S ALGORITHM (SHORTEST PATH)
================================================================================

LOCATION IN CODE: Lines 1006-1144

CONCEPT:
Dijkstra's algorithm finds the shortest path from a source vertex to all
other vertices (or a specific destination) in a weighted graph with
non-negative edge weights.

IMPLEMENTATION:
    struct Edge {
        int destination;
        int distance;
    };
    
    class BloodDeliveryGraph {
    private:
        int numLocations;
        vector<vector<Edge>> adjList;  // Adjacency list
        vector<string> locationNames;
        
    public:
        vector<int> dijkstra(int source, int destination);
        void displayShortestPath(int source, int destination);
    };

ALGORITHM STEPS:
    1. Initialize distances: dist[source] = 0, all others = ∞
    2. Create priority queue (min-heap) with (distance, vertex)
    3. While queue not empty:
       - Extract vertex u with minimum distance
       - For each neighbor v of u:
         - If dist[u] + weight(u,v) < dist[v]:
           - Update dist[v] = dist[u] + weight(u,v)
           - Add (dist[v], v) to queue
           - Set parent[v] = u
    4. Reconstruct path using parent array

EXAMPLE:
    Locations: Blood Bank(0), Hub(1), Hospital A(2), Hospital B(3)
    Routes: 0→1(10), 0→2(30), 1→2(15), 1→3(25), 2→3(5)
    
    Find shortest: 0 → 3
    
    Process:
    - Start: dist = [0, ∞, ∞, ∞]
    - Process 0: dist = [0, 10, 30, ∞]
    - Process 1: dist = [0, 10, 25, 35]  (25 = 10+15)
    - Process 2: dist = [0, 10, 25, 30]  (30 = 25+5)
    
    Shortest path: 0 → 1 → 2 → 3 (distance: 30)

WHY PRIORITY QUEUE?
- Always processes vertex with smallest known distance
- Greedy choice leads to optimal solution
- Without PQ: O(V²), With PQ: O((V+E) log V)

TIME COMPLEXITY:
- O((V + E) log V) with binary heap
- O(V² + E) with simple array

USED FOR:
- Setup delivery network (Menu Option 12)
- Find shortest delivery route (Menu Option 13)
- Real-world: Emergency blood transport optimization

10. MIN-HEAP PRIORITY QUEUE
================================================================================

LOCATION IN CODE: Lines 1146-1310

CONCEPT:
A Min-Heap is a complete binary tree where each parent is smaller than its
children. Used for priority queue where smallest (highest priority) element
is always at root.

IMPLEMENTATION:
    class PatientQueue {
    private:
        vector<Patient> heap;  // Dynamic array
        
        bool hasHigherPriority(const Patient& p1, const Patient& p2);
        void bubbleUp(int index);
        void bubbleDown(int index);
        
    public:
        void enqueue(Patient p);
        Patient dequeue();
        Patient peek();
        int getSize();
    };

HEAP PROPERTY:
    For any node at index i:
    - Parent: (i-1)/2
    - Left child: 2*i + 1
    - Right child: 2*i + 2
    - Parent's priority ≤ Children's priority

PRIORITY ORDER (EDF - Earliest Deadline First):
    1. Urgency level (1=Critical > 2=Urgent > 3=Normal)
    2. If same urgency: Earlier deadline first
    3. If same deadline: Earlier arrival time first

BUBBLEUP (after insert):
    1. Add new element at end
    2. Compare with parent
    3. If higher priority than parent, swap
    4. Repeat until heap property restored

BUBBLEDOWN (after delete):
    1. Remove root (highest priority)
    2. Move last element to root
    3. Compare with children
    4. Swap with higher priority child
    5. Repeat until heap property restored

WHY DYNAMIC VECTOR?
- Original: Fixed array of 100 patients
- Now: Unlimited capacity (grows automatically)
- No artificial limits in emergencies

TIME COMPLEXITY:
- Enqueue: O(log n)
- Dequeue: O(log n)
- Peek: O(1)

USED FOR:
- Add patient to queue (Menu Option 5)
- Display patient queue (Menu Option 6)
- Serve most critical patient (Menu Option 7)

11. BFS (BREADTH-FIRST SEARCH)
================================================================================

LOCATION IN CODE: Lines 305-340 (inside BloodCompatibilityGraph)

CONCEPT:
BFS explores a graph level by level, visiting all neighbors before moving
to next level. Uses a queue (FIFO) to track vertices to visit.

IMPLEMENTATION:
    void BloodCompatibilityGraph::BFS(string startBloodType) {
        vector<bool> visited(NUM_BLOOD_TYPES, false);
        queue<int> q;
        
        q.push(startIndex);
        visited[startIndex] = true;
        
        while (!q.empty()) {
            int current = q.front();
            q.pop();
            cout << bloodTypes[current] << " ";
            
            for (int j = 0; j < NUM_BLOOD_TYPES; j++) {
                if (adjacencyMatrix[current][j] && !visited[j]) {
                    visited[j] = true;
                    q.push(j);
                }
            }
        }
    }

HOW IT WORKS:
    Start from O- (Universal Donor):
    Level 0: O-
    Level 1: O+, A-, A+, B-, B+, AB-, AB+ (all direct donations)
    
    BFS Output: O- O+ A- A+ B- B+ AB- AB+

WHY BFS?
- Explores by levels (distance from source)
- Finds shortest path in unweighted graphs
- Complete exploration of reachable nodes

TIME COMPLEXITY:
- O(V + E) where V = vertices, E = edges

USED FOR:
- BFS on compatibility graph (Menu Option 18)
- Shows blood types reachable from given type in level order

12. DFS (DEPTH-FIRST SEARCH)
================================================================================

LOCATION IN CODE: Lines 343-370 (inside BloodCompatibilityGraph)

CONCEPT:
DFS explores a graph by going as deep as possible before backtracking.
Uses recursion (implicit stack) or explicit stack.

IMPLEMENTATION:
    void BloodCompatibilityGraph::DFSHelper(int current, vector<bool>& visited) {
        visited[current] = true;
        cout << bloodTypes[current] << " ";
        
        for (int j = 0; j < NUM_BLOOD_TYPES; j++) {
            if (adjacencyMatrix[current][j] && !visited[j]) {
                DFSHelper(j, visited);  // Recursive call
            }
        }
    }
    
    void BloodCompatibilityGraph::DFS(string startBloodType) {
        vector<bool> visited(NUM_BLOOD_TYPES, false);
        DFSHelper(startIndex, visited);
    }

HOW IT WORKS:
    Start from O-:
    Path: O- → O+ → A+ → AB+ → (backtrack) → B+ → (backtrack) → ...
    
    DFS explores one complete path before trying alternatives

WHY DFS?
- Memory efficient (only stores current path)
- Good for finding any path (not necessarily shortest)
- Natural for tree-like structures

TIME COMPLEXITY:
- O(V + E) where V = vertices, E = edges

USED FOR:
- DFS on compatibility graph (Menu Option 19)
- Shows depth-first exploration of compatibility

13. INPUT VALIDATION SYSTEM
================================================================================

LOCATION IN CODE: Lines 1327-1366

CONCEPT:
Input validation ensures data integrity by checking user inputs against
predefined rules before processing.

IMPLEMENTATION:
    bool isValidBloodGroup(string bloodGroup) {
        string validGroups[] = {"O-", "O+", "A-", "A+", "B-", "B+", "AB-", "AB+"};
        for (int i = 0; i < 8; i++) {
            if (bloodGroup == validGroups[i]) return true;
        }
        return false;
    }
    
    bool isValidAge(int age) {
        return age >= 1 && age <= 120;
    }
    
    bool isValidPhone(string phone) {
        if (phone.length() < 10) return false;
        for (char c : phone) {
            if (!isdigit(c)) return false;
        }
        return true;
    }
    
    bool isDuplicateID(int id) {
        int index = hashFunc(id);
        Donor *temp = hashTable[index];
        while (temp) {
            if (temp->id == id) return true;
            temp = temp->next;
        }
        return false;
    }

VALIDATION RULES:
- Blood Group: Must match exactly one of 8 valid types
- Age: Must be between 1 and 120
- Phone: Minimum 10 digits, all numeric
- ID: Must be unique (not already in database)

WHY VALIDATION?
- Prevents data corruption
- Maintains database integrity
- User-friendly error messages
- No memory leaks (cleanup on validation failure)

TIME COMPLEXITY:
- Blood group check: O(1) - fixed 8 comparisons
- Age check: O(1)
- Phone check: O(n) where n = phone length
- Duplicate ID check: O(k) where k = chain length at hash

USED FOR:
- Adding donors (Menu Option 1)
- Adding patients (Menu Option 5)
- All user input operations
