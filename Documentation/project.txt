                        1. PROJECT OVERVIEW
================================================================================

PROJECT NAME: Blood Bank Management System

DESCRIPTION:
A full-stack web application for managing blood bank operations including 
donor registration, blood inventory tracking, transaction management, patient 
priority queuing, and blood compatibility checking.

TECHNOLOGY STACK:
┌─────────────────────────────────────────────────────────────────────────────┐
│ Layer          │ Technology           │ Purpose                            │
├─────────────────────────────────────────────────────────────────────────────┤
│ Backend        │ Python Flask         │ Web server, routing, business logic│
│ Backend (Alt)  │ C++ (prog1.cpp)      │ Console-based DSA implementation   │
│ Frontend       │ HTML5 + Jinja2       │ Dynamic web pages                  │
│ Styling        │ CSS3                 │ Responsive UI with gradients       │
│ Icons          │ Font Awesome 6.0     │ UI icons and graphics              │
│ Database       │ Text Files (CSV)     │ Simple file-based storage          │
└─────────────────────────────────────────────────────────────────────────────┘

KEY FEATURES:
• Donor Management - Register, search, and delete blood donors
• Blood Inventory - Track 8 blood types with stock levels
• Transaction Recording - Log donations and blood issues
• Patient Priority Queue - Min-heap based urgency scheduling
• Blood Compatibility - Graph-based compatibility checking
• Earliest Deadline First (EDF) Scheduling for patients

╔═══════════════════════════════════════════════════════════════════════════╗
║ FILE: cpp_Backend/prog1.cpp (~2,200 lines)                                ║
║ TYPE: C++ Console Application                                             ║
║ PURPOSE: DSA-heavy backend with advanced data structures                  ║
╚═══════════════════════════════════════════════════════════════════════════╝

This is the C++ console version implementing 11 DSA features:

1. Hash Table with Chaining (O(1) donor lookup)
2. AVL Tree (Self-balancing BST for donor names)
3. Graph (Blood compatibility adjacency list)
4. Trie (Autocomplete donor name search)
5. LRU Cache (Recent donor access caching)
6. Union-Find (Blood type grouping)
7. Segment Tree (Range queries on inventory)
8. Minimum Spanning Tree (Prim's algorithm for networks)
9. Dijkstra's Algorithm (Shortest path in networks)
10. Min-Heap Priority Queue (Patient scheduling)
11. Input Validation (Age, phone, blood type verification)

See Documentation/code.txt for complete line-by-line explanation.
See Documentation/dsa.txt for DSA concepts explanation.

╚═══════════════════════════════════════════════════════════════════════════╝

FORMAT: ID,Name,Age,Phone,City,BloodGroup,Urgency,Deadline,ArrivalTime

FIELDS:
- ID (String): Unique patient identifier
- Name (String): Full name
- Age (Integer): Patient age
- Phone (String): Contact number
- City (String): Patient's city
- BloodGroup (String): Required blood type
- Urgency (Integer): 1=Critical, 2=Urgent, 3=Normal

- ArrivalTime (Float): Unix timestamp when added to queue

NOTE: Patient data is primarily managed in-memory using the PatientQueue
class. File is used for persistence.

╔═══════════════════════════════════════════════════════════════════════════╗
║ FILE: Data/transactions.txt                                               ║
║ TYPE: CSV (Comma-Separated Values)                                        ║
║ PURPOSE: Log all blood donations and issues                               ║
╚═══════════════════════════════════════════════════════════════════════════╝

FORMAT: Action,DonorID,BloodGroup,Quantity,Timestamp

SAMPLE DATA:
Donation,1001,B+,50,Sat Dec  7 14:30:00 2024
Issue,P001,B+,5,Sat Dec  7 15:45:00 2024
Donation,1002,O+,100,Sat Dec  7 16:00:00 2024
Issue,P002,O+,10,Sat Dec  7 16:30:00 2024

FIELDS:
- Action (String): "Donation" or "Issue"
- DonorID (String): ID of donor (donation) or patient (issue)
- BloodGroup (String): Blood type involved
- Quantity (Integer): Number of units
- Timestamp (String): Human-readable date/time from time.ctime()

TRANSACTION LOGIC:
- Donation: Adds to inventory (inventory[blood_group] += quantity)
- Issue: Subtracts from inventory (inventory[blood_group] -= quantity)

                            5. DATA FLOW
================================================================================

DONOR REGISTRATION FLOW:
========================
User → [donors.html Form] → POST /add_donor → [app.py]
  → read_csv(donors.txt) → append new donor → write_csv(donors.txt)
  → redirect /donors → [donors.html] → Display updated list

BLOOD TRANSACTION FLOW:
=======================
User → [transactions.html Form] → POST /add_transaction → [app.py]
  → read_csv(transactions.txt) → append transaction → write_csv
  → read_csv(inventory.txt) → update quantity → write_csv
  → redirect /transactions → Display updated history

PATIENT QUEUE FLOW:
==================
Add Patient:
  User → [patients.html Form] → POST /add_patient → [app.py]
    → patient_queue.enqueue(patient) → write to patients.txt
    → JSON response → JavaScript updates UI

Serve Patient:
  User → Click "Serve" → POST /serve_patient → [app.py]
    → patient_queue.dequeue() → return patient details
    → JSON response → JavaScript displays served patient

COMPATIBILITY CHECK FLOW:
========================
User → [compatibility.html Form] → POST /check_compatibility → [app.py]
  → check_compatibility(donor_blood, patient_blood)
  → lookup BLOOD_COMPATIBILITY dictionary
  → JSON response → JavaScript displays result

================================================================================
                        7. DSA CONCEPTS USED
================================================================================

IN FLASK APP (app.py):
─────────────────────
1. MIN-HEAP (Priority Queue)
   - heapq module for PatientQueue
   - O(log n) insert and extract
   - Tuple ordering: (urgency, deadline, arrival, patient)

2. DICTIONARY (Hash Map)
   - BLOOD_COMPATIBILITY dictionary
   - O(1) lookup for compatibility check

3. EARLIEST DEADLINE FIRST (EDF)
   - Scheduling algorithm in PatientQueue
   - Deadline-aware patient prioritization

4. LINEAR SEARCH
   - Donor search functionality
   - CSV file parsing

IN C++ BACKEND (prog1.cpp):
──────────────────────────
1. Hash Table with Chaining - O(1) donor lookup
2. AVL Tree - O(log n) balanced donor name search
3. Graph (Adjacency List) - Blood compatibility relations
4. Trie - O(k) autocomplete for donor names
5. LRU Cache - O(1) recent donor caching
6. Union-Find - O(α(n)) blood type grouping
7. Segment Tree - O(log n) range queries
8. Prim's MST - O(E log V) network optimization
9. Dijkstra's Algorithm - O(V log V + E) shortest paths
10. Min-Heap - O(log n) patient priority queue
11. Input Validation - Data integrity checks
